You asked for a standalone app — no fork, no patching of T3 Code. This page explains the investigation, the design, the code I wrote, and how I verified it.

1. The question and the decision

Originally the question was "how hard would a Discord RPC integration be?" I inspected the installed T3 Code build and its upstream repository, then recommended either a sidecar or a fork. You chose the standalone app, so I built the sidecar as a real, self-contained program.

Installed app is Electronapp.asar bundles the desktop client; server.asar bundles a local HTTP/SSE server.
Rich API existsEndpoints like /api/session, /api/session/active, /api/event already expose session data.
No plugin systemNo extension hook in the desktop app, so a fork would be required for in-app integration.
Upstream won't take itThe README says large features are not being accepted; a fork would be a maintenance burden.

Key design choice: instead of fighting the desktop app's auth token (stored in its keyring/state DB), the standalone app reads T3 Code's local SQLite state file directly, read-only. That removes the need for any credentials and keeps the sidecar completely decoupled.

2. How the data is found

I probed statev2.sqlite with Node's built-in node:sqlite (read-only). The active data lives in the orchestration_v2_* tables, not the older projection_threads table:

TableUsed for
orchestration_v2_projection_threadsThread title, project, creation time, last-visited time, model, worktree path, lineage — all in payload_json.
orchestration_v2_projection_runsLatest run status (e.g. running) and run start time (requested_at).
orchestration_v2_projection_subagentsActive subagent tracking (status not in completed/failed/interrupted/cancelled/rolled_back). Drives the Orchestrating N agents presence state.
orchestration_v2_projection_provider_sessionsFallback busy check: status = running / ready etc.
orchestration_v2_projection_runtime_requestsPending requests → a "needs input" state.
projection_projectsHuman-readable project title; falls back to worktree directory name.

Thread selection logic:

  • Skip deleted, archived, snoozed threads. Only genuine subagents are excluded (relationshipToParent: "subagent", createdBy: "agent", or delegated task IDs); user-forked threads are fully supported and retained.
  • Presence follows the focused thread: on Windows, the Electron window title (format project / thread) is probed directly. If unavailable or on non-Windows platforms, it falls back to recent thread.visit-recorded heartbeat events in orchestration_events (recorded every ~10s for the focused thread), followed by command-palette opens (opens.openedAt).
  • A running task does not pin presence; busy status is only used as a tie-breaker when focus times match.
  • Derive status: working (local run active) → orchestrating (subagents running while local run waits) → needs-input → idle.
  • Per-turn run timer: the timer follows the current T3 Code run/turn and resets when a new run begins, matching T3's own 'Working for X' display. When busy, it uses the current run's requested_at; while waiting on subagents, the timer stays anchored to the parent run that spawned those subagents and keeps counting through the wait until the parent starts a new run.
  • Redundant project suffixes (where project equals thread title or "No project") are suppressed from status text.

4. What Discord sees

  "details": "Fix RPC Error",
  "state": "5 agents · 2 threads · 12m",
  "timestamps": { "start": 1763675837 },
  "assets": { "large_text": "Fix RPC Error · Analyze Relationship History" }
}

// Example: Multi-thread running without subagents (fallback)
{
  "name": "T3 Code",
  "details": "Fix RPC Error",
  "state": "Working for 48m across 2 threads",
  "timestamps": { "start": 1763675837 },
  "assets": { "large_text": "Fix RPC Error · Analyze Relationship History" }
}

// Example: Single thread running
{
  "name": "T3 Code",
  "details": "Discord RPC Integration Difficulty",
  "state": "Working for 11m 42s in No project",
  "timestamps": { "start": 1763675837 },
  "assets": { "large_text": "T3 Code · hy4-flash-free" }
}

Discord only permits a single Rich Presence activity per client. When multiple threads are running simultaneously, the bridge summarizes all active work: details features the focused thread headline, state displays compact agent and thread counts with wall-clock active working time when subagents are active (e.g. 5 agents · 2 threads · 12m), falling back to Working for <duration> across N threads when no subagents are active, and assets.large_text joins running thread titles with dot separators.

To respect Discord RPC rate limits, 500ms polling is used, structural changes (thread switches or status changes) are sent immediately (subject to a 5-per-20s safety cap), while ticking duration-only updates are throttled to 5 seconds. Redundant project names (such as "No project" or matching the thread title) are omitted from the status line. Text fields and buttons are truncated safely according to UTF-8 byte limits (128 bytes and 32 bytes respectively).

The timestamps.start field is a 10-digit Unix seconds value representing total T3 Code server uptime (from server-runtime.json), keeping total uptime distinct from active task durations.

5. Verification

Detection verified. npm run once resolved the current thread: title Discord RPC Integration Difficulty, project No project, model hy4-flash-free, status working, with total uptime in appStartMs.
Presence path verified. I ran the app against a fake local Discord IPC pipe that spoke the RPC framing protocol. It completed the handshake, received READY, and sent SET_ACTIVITY with the payload above. Result: PASS.

7. Limitations and gotchas

  • Discord desktop must be running; the bridge reconnects automatically when it appears.
  • It reads T3 Code's internal SQLite schema. A T3 Code update could change that schema — rerun npm run once to diagnose.
  • Discord elapsed timer reflects total T3 Code uptime (from server-runtime.json startedAt). The active task's duration is displayed directly in the status line (e.g. Working for 11m 42s in <project>) when working, while idle shows no working duration.
  • No credentials are used or stored; the database is opened strictly read-only.
  • You must supply your own Discord application ID and assets — the project intentionally ships none.
  • Only the desktop/server machine can show this presence; web/mobile clients can't drive Discord RPC.
  • The IPC pipe override was added mainly for testing, but is also handy if multiple Discord clients are running.
